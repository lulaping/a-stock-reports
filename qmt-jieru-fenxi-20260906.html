一、现状盘点：模拟盘离实盘有多远

tick-stock-panel 的 AI 交易员模块（app/custom/aitrader）已具备完整的「策略 → 风控 → 撮合 → 审计 → 监控」闭环，其中只有撮合层是模拟的，其余模块在实盘中可直接复用或小幅适配：

模块现状实盘价值
策略评估引擎6 种策略类型 + 动态交易员注册表，20s tick 轮询选股出信号直接复用
风控链时段门控/T+1/涨跌停/流动性/回撤红线滞回/紧急停机/交易员级开关复用 + 实盘护栏强化
账户管理动态增删/停用/审计日志/风控事件流/净值序列直接复用
监控 UI订单流水/成交流水(120天)/归因分析/净值对比/管理页直接复用
行情管道enriched 增量行情(腾讯/雪球源)复用为主，xtdata 可作对照源
撮合层_apply_fill：按现价即时 100% 成交，无滑点/排队/部分成交必须重写为真实回报链路

三、接入架构：BrokerAdapter 双实现

核心思路：把「下单执行」抽象为 BrokerAdapter 接口，模拟盘与实盘成为两个可切换实现，上层策略/风控/账户/UI 全部不动：

tick-stock-panel (FastAPI · Windows 本机 · 与 miniQMT 同机 ✅)
 ├─ 策略评估层 (strategies.py 6 策略类型)     ── 不变
 ├─ 风控层 (validate_order / 回撤红线 / 停机)  ── 不变 + 实盘护栏
 ├─ ★ 执行层 BrokerAdapter (新增抽象)
 │    ├─ SimBroker   = 现有 _apply_fill 模拟撮合 (保留 → 模拟盘继续跑)
 │    └─ QmtBroker   = xtquant 桥 (order_stock → 回报状态机 → 对账)
 │         └─ miniQMT 客户端 (本机登录) → 国金柜台
 └─ 前端 (订单/成交/净值/归因/管理页)          ── 不变 + 实盘模式开关
模拟 vs 实盘的关键差异现状（模拟）实盘（QMT）改造点
成交模型按现价即时全额成交委托 → 部分成交/全部成交/废单/撤单，需实现回报状态机（on_stock_order / on_stock_trade 回调驱动）
资金/持仓引擎内部记账定期与券商对账（query_stock_asset / positions），防错单漂移；T+1 可用数量以券商 can_use_volume 为准
多交易员每交易员独立 10/30 万虚拟账户实盘只有一个资金账户：多交易员需「虚拟份额记账 + 合并下单」，或先只映射 1 个交易员实盘
价格无滑点限价/五档市价，需滑点与废单处理（涨跌停无法成交等）
故障语义无xtquant 断线（on_disconnected）→ 自动熔断 + 人工介入

四、改造工作量评估

工作项规模说明
BrokerAdapter 抽象 + SimBroker 重构中现有 place_order/_execute_signal 调用点收敛到接口
QmtBroker（下单/回报状态机/对账/断线熔断）大核心工程；回报与订单流水的幂等关联（order_remark 载 trader_id+signal）
实盘风控护栏中单日最大下单笔数/金额、下单冷却、连续废单熔断、启动需手动解锁
前端实盘模式 + 下单二次确认小模拟/实盘模式徽章已具备（BETA 标签处扩展）
程序化交易报备材料整理小低频策略报备内容简单（见下节）

总体量级估计：2~4 周（熟悉两边代码、单人投入；不含模拟盘策略验证期）。此为经验估计，实际以开发过程为准。

五、合规要求：程序化交易报备（个人也要做）

事项要求
监管依据《证券市场程序化交易管理规定（试行）》 + 沪深北交易所实施细则（2025 年下半年起陆续施行），原则「先报告、后交易」
报备内容账户基本信息、资金规模、策略类型及主要内容、交易指令执行方式、最高申报速率/单日最高申报笔数、交易软件名称（迅投 QMT/自研）、开发主体等
对本项目的影响当前 20s tick + 日级调仓属低频，报备内容简单；切勿升级为 tick 级高频（高频另有额外报告义务与更高监控标准）；策略/软件重大变更需在下月初前变更报告
违规后果未报备/虚报被监测到 → 限制量化通道甚至账户限制

六、风险清单

  • 🔴 误单风险：全自动实盘的第一单前必须有护栏（单日限额 + 冷却 + 熔断 + 二次确认），且先经 P1/P2 阶段验证 —— 现有模拟盘从未经历过「真实废单/部分成交」路径
  • 🔴 链路单点：miniQMT 客户端必须本机在线登录，xtquant 断线（on_disconnected）须自动熔断停机；本机 Windows 重启/断网 = 交易中断
  • ⚠️ 回测乐观偏差：模拟撮合按现价全额成交，胜率/收益天然偏乐观；实盘滑点、排队、涨跌停不可成交会侵蚀收益 —— 模拟盘统计不可直接外推
  • ⚠️ 多交易员 vs 单账户：实盘只有一个资金账户，多交易员「虚拟份额」记账有归属歧义（同一票被两个交易员同时持有），建议首期只映射 1 个交易员
  • ⚠️ 外部依赖变动：xtquant 版本升级 API 可能变动；国金门槛/费率政策随时调整（2026 年已多次口径变化）
  • ✅ 本机 Windows + 本地 Python 与 xtquant 天然同栈，无跨机部署问题
  • ✅ 低频日级策略远离高频监管阈值，报备简单

七、备选方案对比（诚实评价）

方案优势劣势结论
miniQMT + xtquant（国金）本地 Python 全自由、门槛 10 万、与现有系统同机同栈、回调/查询 API 完整需客户端在线、无回测、单机依赖★ 首选
PTrade（恒生，国金同步提供）云端托管、断电断网策略仍在跑、稳定策略必须写在其内置环境，无法与 tick-stock-panel 直连，只能信号导出+人工搬运架构不匹配
掘金量化回测+仿真+实盘平台化，文档好需用其 SDK 与终端体系，现有面板/交易员体系整合弱，等于重写执行+监控备选
easytrader 等客户端自动化无资金门槛、任意券商模拟键鼠/内存读取性质灰色、易随客户端升级失效、无回报回调，不建议实盘主力不推荐
券商条件单/网格工具零代码、稳定无法实现自定义多策略 AI 交易员逻辑能力不足

八、建议路线图

阶段内容风险敞口
P0 现在模拟盘持续跑策略 + 归因分析，积累各交易员胜率/回撤统计（交易员管理/归因页已就绪）零
P1 只读对接开通国金 miniQMT（客户经理渠道）+ 完成程序化报备；xtquant 只读接入：每日对账资金/持仓、行情对照 —— 零下单零
P2 半自动BrokerAdapter 上线：AI 信号 → 前端人工确认 → 一键 QMT 下单；回报/对账全链路验证每笔人工把关
P3 全自动灰度单交易员 + 小资金 + 护栏（单日限额/熔断）全自动，逐步放量；其余交易员保持模拟小资金可控
正向信号：模拟盘已具备实盘管理的一切「外围能力」（订单/成交/审计/风控事件/归因/管理 UI），接入 QMT 是替换执行内核而非重建系统 —— 这正是当前架构最大的先发优势。
可行性高。xtquant 本地 Python 模式与 tick-stock-panel（Windows + FastAPI + Python）同机同栈，策略/风控/账户/管理层约 80% 复用，核心工程集中在 QmtBroker 回报状态机与对账
前置条件国金 miniQMT：20 日日均资产 ≥10 万 + 风评 C4+ + 客户经理渠道办理；程序化交易报备（个人必须，低频策略报备简单）
最大风险非技术，而是「模拟成交假设过优」直接实盘 —— 必须按 P1 只读 → P2 半自动 → P3 全自动灰度推进，护栏先于自动化
不确定性声明门槛/费率/风评等级等政策信息存在渠道分歧且随时可变，以国金官方最终审核为准；xtquant API 兼容性以实际版本实测为准
⚠️ 风险提示：本报告为技术可行性评估，不构成投资建议。量化实盘存在本金亏损风险，模拟盘历史表现不代表实盘收益；程序化交易须依法履行报备义务。
